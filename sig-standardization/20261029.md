### Possible new KaaS standards through DISA Kubernetes STIG

sponsor: @janiskemper

- recall from last meeting
- possible new standards based on the best practices mentioned in the DISA Kubernetes STIG
  - Gardener test tool [diki](https://github.com/gardener/diki), [DISA k8s STIG](https://github.com/gardener/diki/blob/main/docs/rulesets/disa-k8s-stig/ruleset.md) ruleset
- proposal 1: providers should offer a table such as [this one from Gardener](https://gardener.cloud/docs/security-and-compliance/kubernetes-hardening/) as to how these guidelines are satisfied (or can be satisfied via config if desired)
  - apparently, Gardener has this table;
  - Syself intends to offer such a table for ClusterStacks;
  - others could follow suit (whether we make an SCS standard or not)
- proposal 2: identify uncontroversial subset of the rules and find ways to push these rules within SCS
  - such as etcd encryption (however: some argue that secrets don't belong in etcd at all)
  - be careful to avoid too narrow boundaries (BTW also for our current standards!)
  - be careful as well to stick to things that can be tested automatically
- note: (baseline) security as interoperability
  - if you want to switch to another vendor, you expect a certain baseline
  - also improve credibility of smaller vendors (technical excellence instead of name brand)
- start out with transparency (proposal 1)
  - maybe begin with a blog post (@janiskemper?)

### WIP: ongoing overhaul of certification tooling

sponsor: @mbuechse

- in the context of the general restructuring of the standards repo and software development process, see issue [standards#1192](https://github.com/SovereignCloudStack/standards/issues/1192)
  - the compliance monitor and the test suite had to be not only factored out of the standards repo (via forking), but also disentangled from each other
  - to this end, I devised an update of the general concepts in SCS-0003-v2
  - I completely removed the business logic from the compliance monitor (namely, aggregating results from multiple testcases and even multiple subjects): a separate aggregation step is now required that produces a formal report for the composite testcases/subjects
  - **@mbuechse to show 'live' demo of current state of this line of work**
  - note: will make (automated) handling of outdated/new k8s minor versions easier; compare with current PR [standards#1298](https://github.com/SovereignCloudStack/standards/pull/1298)
- see also
  - PR [standards#1289](https://github.com/SovereignCloudStack/standards/pull/1289) for new concepts 'attestation' and revised 'report', 'scorecard'
  - repo [compliance-monitor](https://github.com/SovereignCloudStack/compliance-monitor)
  - repo [test-suite](https://github.com/SovereignCloudStack/test-suite)
- open tasks for the 'switch' (to make this WIP productive)
  - improve documentation of the test reports (testcase description)
  - conduct a break-out session to identify what's missing feature-wise
  - PR on standards repo that removes compliance monitor and test suite, referring people to the new repositories
  - add test-suite to Zuul config
- ideally try to switch soon, so we don't diverge too much
  - currently not many changes are pending on the standards repo that would have to be ported forward to the new repos
- FYI HTML rendering of compliance monitor is (and has always been) primarily intended for internal and debugging purposes; it is being mirrored on the docs page; if more elaborate frontend is desired, it should be implemented as a separate service that merely fetches data from the compliance monitor in JSON format via some HTTP endpoint
  - cf issue [standards#1297](https://github.com/SovereignCloudStack/standards/issues/1297)
